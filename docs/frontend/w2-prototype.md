# W2 Lab 前端原型（低保真）

| 项 | 内容 |
|---|---|
| 版本 | v1.0 |
| 日期 | 2026-11-09 |
| 阶段 | W2（2026-11-09 — 11-13） |
| 范围 | 仅 ChatView（流式对话）与 ExtractView（公文要素抽取） |
| 状态 | 待实现；本文件是页面与交互的唯一原型依据 |
| 关联文档 | `docs/api/API_CONTRACT.md` 第 2 章、`docs/frontend/FRONTEND_DEV_GUIDE.md` 第一部分 |

> 这是**低保真原型**：只定义信息架构、页面区域、组件职责、状态和交互，不定义颜色、字号、间距等视觉细节，也不包含任何代码。W2 的目标是跑通"流式 + Prompt 变量 + 结构化抽取"，不是做完整产品。

## 0. 为什么先写原型

原型不是"画好看"，而是在写代码前锁定四件事：

1. **页面里有什么**（信息架构与区域划分）——避免写着写着临时加需求；
2. **每个区域归哪个组件管**（组件职责）——避免所有逻辑堆在一个页面里；
3. **会出现哪些状态**（空/加载/流式/完成/停止/错误）——流式应用最容易漏状态；
4. **交互如何映射到接口**（API 与 SSE 事件）——保证前后端契约一致。

W2 的原型只回答这些问题，不追求视觉稿。视觉细节留到完整项目阶段。

## 1. 范围与非目标

### 1.1 本阶段页面

| 页面 | 路由 | 用途 |
|---|---|---|
| ChatView | `/chat`（默认重定向） | 输入问题，看流式回答、风格变化与首字耗时 |
| ExtractView | `/extract` | 粘贴公文文本，查看结构化字段与 warnings |

### 1.2 明确不做

- 登录/注册、路由守卫、用户菜单；
- 会话历史、会话侧栏、消息持久化；
- 知识库上传、引用卡片、执行轨迹、工具开关；
- 心理健康业务域、危机卡片、隐私拒绝；
- Element Plus 等完整 UI 库（W2 可用原生 CSS，完整项目再引入）；
- 深色模式、复杂动画、多语言。

> 划定"不做"不是偷懒，而是保护 W2 唯一硬检查：10 分钟干净环境跑通流式。每多一个依赖，演示失败面就大一分。

## 2. 信息架构

```text
W2 Stream Lab
├─ /chat       流式对话（默认页）
├─ /extract    公文要素抽取
└─ 顶栏状态     DeepSeek 健康状态（可选，来自 /api/health 或 /actuator/health）
```

导航规则：

- 顶栏两个入口：`流式对话`、`公文抽取`；当前页高亮。
- 默认路由 `/` 重定向到 `/chat`。
- W2 不做权限控制；刷新页面允许丢失对话内容（无持久化）。
- 页面切换时若有流式请求，先中止再离开，避免请求泄漏。

## 4. 页面一：ChatView（流式对话）

### 4.1 页面线框

```text
┌──────────────────────────────────────────────────────────────┐
│ 回答风格： (严谨)  (温和)  (简洁)                              │
├──────────────────────────────────────────────────────────────┤
│  消息区（可滚动）                                             │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ [用户] 用三句话解释什么是 SSE                            │  │
│  └────────────────────────────────────────────────────────┘  │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ [助手] SSE 是一种……▌                                    │  │
│  │                                                        │  │
│  │ 首字 0.9s / 总 4.2s                                    │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
│  ┌ 错误提示 ─────────────────────────────────────────────┐  │
│  │ 模型响应超时，请稍后重试。         [重试]              │  │
│  └────────────────────────────────────────────────────────┘  │
├──────────────────────────────────────────────────────────────┤
│  ┌──────────────────────────────────────────────┐  [发送]   │
│  │ 输入问题，Enter 发送，Shift+Enter 换行        │           │
│  └──────────────────────────────────────────────┘           │
│  0/4000                                    流式中：[停止]    │
└──────────────────────────────────────────────────────────────┘
```

区域职责：

| 区域 | 职责 |
|---|---|
| 风格选择 | 发送时把 `style` 传给后端；切换只影响下一次发送 |
| 消息区 | 展示用户/助手消息；流式时显示光标；只在接近底部时自动跟随 |
| 耗时信息 | 首字耗时与总耗时；开发/演示模式可见 |
| 错误提示 | 保留已生成内容，提供重试；不把原始异常暴露给用户 |
| 输入区 | 校验 1–4000 字符；空内容禁用；流式中禁用发送、显示停止 |
| 字数提示 | 实时字数，避免提交后才发现超限 |

### 4.2 组件划分

```text
ChatView（页面编排、状态持有）
├─ StyleSelect          风格选择
├─ MessageList          消息列表与滚动策略
│  ├─ ChatMessage       单条消息（用户/助手）
│  │  └─ MarkdownRenderer  仅助手消息使用
│  └─ EmptyState        空态示例问题
├─ StreamStatus         首字/总耗时、流式状态
├─ ErrorNotice          错误与重试
└─ ChatInput            输入、发送、停止
```

划分原则：

- **ChatView 管流程**：发送、停止、重试、页面切换中止；
- **子组件只管展示与本组件交互**，不直接发请求；
- **MarkdownRenderer 单独存在**，因为它是 XSS 风险点，必须能单独测试；
- **ChatMessage 不区分业务状态**，只接收消息对象与 `streaming` 标记。

### 4.3 页面状态

| 状态 | 触发 | 界面表现 | 允许操作 |
|---|---|---|---|
| 空态 | 首次进入 | 示例问题、风格选择、输入框 | 输入/发送/切换风格 |
| 输入无效 | 空内容或 >4000 字 | 发送禁用 + 字数提示 | 修改输入 |
| 请求中（首 token 前） | 点击发送 | 助手占位 + 加载态；发送禁用 | 停止 |
| 流式中 | 收到首个 token | 逐字追加 + 光标 | 停止、滚动 |
| 已完成 | 收到 `done` | 光标消失，显示总耗时 | 继续提问 |
| 已停止 | 用户点击停止 | 标记"已停止"，保留部分内容 | 重试/继续 |
| 错误 | 收到 `error` 或网络失败 | 错误提示 + 保留部分内容 | 重试 |
| 降级 | 首 token 前失败 | 可回退一次非流式 `/api/chat` | 重试/继续 |

> 流式应用的 bug 大多不是"文字不显示"，而是**状态没定义**：停止后按钮没复位、错误后还能重复发送、切换页面后旧 token 还在追加。原型阶段先枚举状态，就是在消灭这类 bug。

### 4.4 交互规则

| 交互 | 行为 | 为什么 |
|---|---|---|
| Enter | 发送 | 聊天场景的高频操作 |
| Shift+Enter | 换行 | 保留多行输入能力 |
| 发送 | 本地立即插入用户消息 + 助手占位，再发起流式请求 | 让用户立刻看到反馈，不被网络延迟"卡住" |
| 停止 | AbortController 中止请求；标记已停止；保留已收到内容 | 用户必须能随时退出长回答 |
| 重试 | 使用相同输入重新发送；不重复插入用户消息 | 失败恢复不应制造重复消息 |
| 切换风格 | 只更新下一次请求的 `style` | 避免用户以为已发送消息被改写 |
| 自动滚动 | 仅当用户处于底部附近时跟随；上滑后不强制拉回 | 允许用户回看历史；避免"抢滚动条" |
| 页面切换/离开 | 中止进行中的请求并清理计时器 | 防止旧请求把消息追加到新页面 |
| 首 token >3s | 显示"模型响应较慢"提示，不自动失败 | 超时由后端判定，前端只负责告知 |
| 兼容性降级 | 首 token 前请求失败，可回退一次非流式 `/api/chat` | 提升演示成功率；已输出后不降级，避免重复内容 |

### 4.5 SSE 事件到界面的映射

| 事件 | 收到后做什么 | 界面变化 |
|---|---|---|
| `meta` | 记录 messageId；进入"请求中" | 助手占位、停止按钮可用 |
| `token` | 追加 `delta` 到助手内容；记录首个 token 时间 | 逐字显示、光标闪烁 |
| `done` | 停止加载；记录总耗时、usage、finishReason | 光标消失、显示耗时 |
| `error` | 保留已生成内容；记录错误码 | 错误提示 + 重试 |
| `: ping` | 忽略，只用于保持连接 | 无 |
| 流结束但无 `done` | 视为异常，提示"连接中断" | 标记已停止/失败，保留内容 |

规则：

- 不使用 EventSource，必须用 `fetch` POST + `Authorization` + `ReadableStream`；
- 解析器必须处理半包、`\r\n`、多行 `data:`、注释心跳；
- 30–50ms 节流更新 Markdown，避免每个 token 全量渲染造成卡顿；
- 代码高亮可在 `done` 后执行；
- 首字耗时以"首个 `token` 事件到达"为准，并在界面注明计时口径。

### 4.6 ChatView 验收清单

- [ ] 空态展示示例问题，输入为空时发送禁用；
- [ ] 发送后逐字显示，长输出不截断；
- [ ] 首字耗时可见且 ≤3s（记录证据）；
- [ ] 切换"严谨/温和/简洁"后，输出语气有可解释变化；
- [ ] 停止生成后保留部分内容并标记已停止；
- [ ] 模型超时/429 显示可读错误，有重试入口；
- [ ] Markdown 正常渲染；XSS payload 不执行；
- [ ] 自动滚动不抢用户滚动条；
- [ ] 页面切换/离开时请求被中止；无重复消息。

区域职责：

| 区域 | 职责 |

| 抽取按钮 | 请求中禁用；显示加载态 |
| 结果区 | 展示 5 个字段；空字段显示"未识别"，不显示 `null` |

### 5.2 组件划分

```text
ExtractView（页面编排）
├─ SampleButtons       示例文本

├─ ExtractSubmit       抽取按钮 + loading
├─ FieldGrid           字段卡片（docType/title/addressee/signature/date）
└─ WarningList         warnings 展示
```

### 5.3 页面状态

| 状态 | 触发 | 界面表现 |
|---|---|---|
| 空闲 | 首次进入 | 空文本、按钮禁用或可用、空结果区 |
| 输入无效 | 空文本或 >8000 字 | 提示原因，抽取按钮禁用 |
| 请求中 | 点击抽取 | 按钮 loading，输入区只读 |
| 成功 | 返回完整字段 | 字段卡片 + 无警告 |
| 兜底 | 返回空字段 + warnings | 字段显示"未识别" + 黄色警告 |
| 错误 | 网络/服务异常 | 错误提示 + 重试，不白屏 |

### 5.4 交互规则

| 交互 | 行为 | 为什么 |
|---|---|---|
| 点击示例 | 覆盖文本域内容 | 演示可重复、稳定 |
| 开始抽取 | 校验后请求 `/api/extract` | 输入校验前置，减少无效调用 |
| 空输入 | 禁止提交并提示 | 后端同样会返回 400，前端先挡一次 |
| 超长输入 | 超过 8000 字禁止提交 | 与契约保持一致 |
| 解析失败 | 展示 warnings，不显示红色系统错误 | 这是"需人工核对"的业务兜底，不是系统崩溃 |
| 清空 | 清空输入与结果 | 便于下一次演示 |

## 8. 响应式与可访问性

- **桌面优先**：内容区最大宽度约 1000px；聊天区高度自适应，输入区固定在内容区底部。
- **移动端**：单列布局；输入区不遮挡消息；结果卡片纵向排列；表格/字段不横向溢出。
- **键盘**：Enter 发送、Shift+Enter 换行、Tab 可遍历、Esc 关闭提示（如有）。
- **焦点**：请求中禁用发送但保留停止按钮可聚焦。
- **读屏**：流式消息用 `aria-live="polite"` 区域，避免逐 token 打断读屏（可按节流后的文本块更新）。
- **对比度**：低保真阶段不定义颜色，但实现时保证正文与背景对比度达标。

## 9. 实现顺序（先骨架后联调）

1. 静态布局：顶栏、两个页面、空态与输入区；
2. 假流式：用本地定时器模拟 `token`，只验证状态机与渲染；
3. 真接口：接 `/api/chat/stream`，修半包、截断、心跳；
4. Prompt 变量：风格选择贯通到后端并对比输出；
5. Markdown 与 XSS：DOMPurify、代码高亮、外链安全；
6. 抽取页：接 `/api/extract`，处理成功/兜底/错误；
7. 体验与验收：停止、重试、自动滚动、移动端、干净环境彩排。

> 先假流式再接真接口，是为了把"状态机 bug"和"网络/后端 bug"分开排查。否则一次性联调，出了问题很难定位。

## 10. 原型评审问题清单

实现前确认：

- [ ] 只做两个页面，没有偷偷加登录/历史/知识库；
- [ ] 每个状态都有明确界面，不需要开发时临时发明；
- [ ] 每个交互都能映射到契约中的接口或事件；
- [ ] 停止、重试、切换页面都有清理方案；
- [ ] 首字计时的口径写清楚（从 fetch 开始还是首个 token）；
- [ ] 抽取失败走 warnings，不把模型原始输出直接展示；
- [ ] Markdown 渲染链明确 `html:false` + DOMPurify；
- [ ] 原型中没有视觉细节歧义，颜色/间距留给实现阶段。
